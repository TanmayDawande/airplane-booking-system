Assessment 8: front end and database connectivity

About 3 minutes
Teammate 1Introduction and interface walkthrough. Face on camera.
  1. Title and purpose (0:00–0:40). Say: “Our project is SkyReserve, an airline reservation system. It stores airports, airlines, aircraft, flights, passengers, bookings, payments and audit logs in a normalized MySQL database.”
  2. Front end (0:40–1:30). Show the home page, the search form (origin, destination, date, cabin), the flights page, the seat map page and the Admin page. Mention the forms, tables and menus.
  3. Database connection (1:30–2:00). Click the MySQL badge in the header. Show host localhost:3306, database airline_db, table count and the IST timezone. This proves the front end is talking to MySQL, not a local file.
Teammate 2Insert a record and verify it in Workbench. Face on camera.
  1. Sign in (2:00–2:15). Open Sign in and use admin / password123. Point out that the header now shows the signed-in user and the IST clock.
  2. Insert through the form (2:15–2:45). Open Admin, click Add passenger, and enter a new passenger. Submit it. Point to the green confirmation box: passenger ID, name, email and recorded time in IST.
  3. Retrieve it (2:45–3:00). Switch to the Passengers tab and search for the new passenger by name or email. The row is read back from MySQL.
  4. Show the table in Workbench (3:00–3:30). In MySQL Workbench run:
    USE airline_db;
    SELECT * FROM passengers ORDER BY passenger_id DESC LIMIT 5;
    Point to the same passenger ID and the created_at timestamp. This is the database proof for Assessment 8.

Assessment 9: database operations and back end

About 4 minutes
Teammate 1Back-end code and full CRUD.
  1. Back end (0:00–0:50). Open app.py and show one route, for example /api/flights. Then open models.py and show the parameterized SQL in FlightModel.create, update and delete. Explain: browser → Flask route → model method → PyMySQL → MySQL airline_db; parameters prevent SQL injection.
  2. INSERT (0:50–1:30). On Admin, click Schedule flight. Add AI-999, BOM → DEL, fare ₹5,200, a future departure date. Submit it and point to the new row.
  3. UPDATE (1:30–2:05). Click Edit on AI-999, change the fare to ₹5,600 and status to Delayed, save. Show the row. In Workbench run:
    SELECT flight_id, flight_number, base_fare, status
    FROM flights WHERE flight_number = 'AI-999';
  4. DELETE (2:05–2:35). Click Delete on AI-999 and confirm. Show that the row is gone and run:
    SELECT * FROM flights WHERE flight_number = 'AI-999';
    The result must be 0 rows.
Teammate 2Joins, aggregation, subquery and triggers.
  1. Five-table join (2:35–3:05). Open Queries and reports and scroll to Full itinerary (five-table join). Explain how the foreign keys connect bookings, passengers, flights, airlines and airports.
  2. GROUP BY + HAVING (3:05–3:30). Show the Airline revenue above ₹5,000 table. Explain COUNT, SUM, AVG and the HAVING filter.
  3. Nested subquery (3:30–3:50). Show Passengers above the average fare. Explain the inner SELECT AVG(total_amount).
  4. Trigger proof (3:50–4:15). Open the Audit log tab in Admin. Show that inserts and updates in bookings and flights automatically created audit rows with IST timestamps.

Assessment 10: complete workflow and validation

About 5 minutes
Teammate 1Login, search, validation and booking.
  1. Login and authentication (0:00–0:35). Open Sign in. First enter a wrong password and show the error. Then sign in as tanmay / password123. Show the username in the header.
  2. Search (0:35–1:05). From the home page, search BOM → DEL on the date shown. Show the matching flights, cabin fare and available seats.
  3. Seat selection (1:05–1:45). Open a flight, point out occupied seats, choose an open seat, and show the fare breakdown update.
  4. Invalid input (1:45–2:15). Try a malformed email or phone number and show the server-side error. Then fill valid passenger details. Also show that selecting an already occupied seat is blocked.
  5. Confirm the transaction (2:15–2:40). Click Confirm & Pay Now. Point out that the booking and payment are written in one atomic transaction. The boarding pass opens with a PNR.
Teammate 2Verification, cancellation and conclusion.
  1. Boarding pass output (2:40–3:10). Show the PNR, passenger, route, departure time in IST, seat and barcode. Print or save as PDF.
  2. Verify the transaction (3:10–3:55). In MySQL Workbench run:
    USE airline_db;
    SELECT b.pnr, b.booking_date, b.seat_number, b.status,
           p.transaction_id, p.amount, p.payment_status, p.payment_time
    FROM bookings b
    JOIN payments p ON b.booking_id = p.booking_id
    WHERE b.pnr = '<YOUR_PNR>';
    Show both the booking and payment rows, with IST timestamps.
  3. Cancel and release the seat (3:55–4:30). Open My bookings, enter the PNR, click Cancel booking. Show the status becomes CANCELLED, payment REFUNDED, and the seat is available again on the seat map. Verify with:
    SELECT b.pnr, b.status, p.payment_status
    FROM bookings b
    JOIN payments p ON b.booking_id = p.booking_id
    WHERE b.pnr = '<YOUR_PNR>';
  4. Reports and conclusion (4:30–5:00). Open Queries and reports, show one summary, and conclude that the front end, Flask back end and MySQL database work as one integrated application.
